# ADR 0032: Probe the drives behind an HPE Smart Array controller

- Status: Accepted
- Date: 2026-10-17
- Extends: [ADR 0004](0004-smartctl-json-as-data-source.md), [ADR 0005](0005-drive-discovery-and-identity.md), [ADR 0016](0016-test-strategy.md), [ADR 0028](0028-logical-volumes-and-enclosures.md), [ADR 0029](0029-notification-field-device-id.md)

## Context

FR-103 asks the tool to find the physical drives behind an HPE Smart Array controller by probing, experimental in version 1 and possible to switch off; the sources of [ARCHITECTURE.md](../../ARCHITECTURE.md) section 5 have named the probe `cciss,N` since milestone M2. Such a controller in RAID mode hides its physical drives from the device scan ([Research 04](../research/04-hardware-raid.md)), and smartctl reaches them with `-d cciss,N`, where `N` is the position of the drive in the device list of the controller.

What is known, checked in the source of smartmontools 7.4 and 7.5 and in its manual page on 2026-10-17 ([Research 08](../research/08-public-recordings.md)):

- `-d cciss,N` accepts `0 <= N <= 127` (`os_linux.cpp`, 7.5 lines 3579 to 3584) and wraps the device as `sat,auto`, so a SATA drive behind the controller is read through SAT (line 3584).
- With the driver `hpsa` the device node is the SCSI generic node of the controller: `smartctl -a -d cciss,0 /dev/sg2` (`smartctl.8.in`, lines 685 to 701).
- `N` indexes the list that `CISS_REPORT_PHYS` answers with (`cciss.cpp`, `cciss_getlun`, lines 197 to 246). A position beyond the list makes the ioctl fail with `-ENXIO` ("give up, assume no device there", lines 87 and 145), which smartctl reports as a failed open with exit status 2 (`smartctl.cpp`, lines 1552 to 1561). The IDs are therefore the positions in the list of devices that are present, not bay numbers.
- smartctl itself expects the option on hosts with the driver `hpsa` only: `is_hpsa_in_raid_mode` compares the `proc_name` with `hpsa`, derives the host number from the SCSI device name `H:C:T:L`, and asks for `-d cciss,N` when the volume reports a RAID level (`os_linux.cpp`, lines 3363 to 3414 and 3475 to 3477). The same controllers run with the driver `smartpqi` on other hosts, and neither a source nor a recording shows that the pass-through works there.
- `-n` (`--nocheck`) is accepted for ATA and SCSI devices and ignored where the power mode check is not supported (`smartctl.8.in`, lines 891 and 930). Both of its paths implement the check with the same message and the same exit status: `ataprint.cpp` line 3448 and `scsiprint.cpp` line 3575 in 7.5 write `Device is in <mode> mode, exit(<n>)`. A call that ends there carries no data and is a standby answer, not an unreadable drive, for every device type (ADR 0004).
- The kernel names a SCSI device `H:C:T:L`: `drivers/scsi/scsi_sysfs.c` (`scsi_sysfs_device_initialize`) sets the name from `host_no`, `channel`, `id` and `lun`, and `drivers/scsi/sg.c` creates the class device of `sgN` below it (`device_create(&sg_sysfs_class, &scsidp->sdev_gendev, …)`), which is what `/sys/class/scsi_generic/sgN/device` points at.

The maintainer decided on 2026-10-17 on three points: the probe runs only where smartctl itself supports it, that is on hosts with the driver `hpsa`; a host with `smartpqi` is detected and named in `scan` and `doctor` but not probed until a source or a recording shows that it works (Q-R2); and every `cciss` form is read with `--nocheck=standby`, so that a drive in standby is not woken. The last point reverses an earlier decision of the same day, which had left the option out for `cciss,N`; FR-203 and [ADR 0012](0012-read-only-and-coexistence-with-smartd.md) stay as they are.

## Options considered

1. **Probe `hpsa` and `smartpqi` alike.** Wider coverage, but it would send the pass-through ioctl to a controller whose driver smartctl does not itself use for it, and no recording shows what comes back.
2. **Probe `hpsa`, name `smartpqi`.** The tool probes where smartctl's own rule points, and a host with `smartpqi` is told what it can do instead: add the drives as manual entries.
3. **Do not probe at all.** FR-103 would not be met, and an administrator would have to look up device IDs by hand.

## Decision

Option 2, with the following rules.

- **Scope.** A SCSI host whose driver is `hpsa` is probed; the driver is read from `/sys/class/scsi_host/hostN/proc_name` ([ADR 0030](0030-controllers-whose-drives-cannot-be-queried.md)). A host with `smartpqi` is not probed: `scan` and `doctor` name it, the reason and the way out, which is a manual entry in `[[discovery.device]]` (FR-104). Any other driver is either no drive controller at all or not a controller the tool probes; the legacy `cciss` driver is a Smart Array driver as well, and it is not probed, because the tool has no source that it occurs on a Proxmox VE 9 host (Research 04).
- **The node.** The probe reads the lowest-numbered `/dev/sgN` whose SCSI device belongs to that host, found through `/sys/class/scsi_generic/sgN/device`; the kernel names that SCSI device `H:C:T:L` and the link's target ends in that name (`drivers/scsi/scsi_sysfs.c`, `drivers/scsi/sg.c`). smartctl derives the host of a block device the same way (`is_hpsa_in_raid_mode`). Any node of the controller reaches it, because the pass-through is an ioctl that looks the drive up in the device list of the controller; the lowest number makes the choice the same within a run and as stable as the numbering of the nodes itself. The identity of a drive does not depend on the node (FR-105): a changed node changes its location, not its state.
- **The reads.** `cciss,0` upwards, one call per ID with the configured detail level, until `CONSECUTIVE_FAILURES` = 3 IDs in a row answer nothing, and never above 127. Three, because a drive that is present but answers nothing must not end the probe, and an ID that is not there fails fast, so three failing calls are what a controller with no drive left costs at most. A call that hangs costs its full timeout, so a wedged controller costs up to three timeouts (30 s by default, NFR-08) per run. A drive that answers goes through the normal examination: logical volume, non-disk, no SMART, exclude rules and identity apply to it as to every other device, and a drive that the scan found as well is kept once (FR-106).
- **The standby check.** Every `cciss` form, `cciss,N` as well as `sat+cciss,N` and `scsi+cciss,N`, is read with `--nocheck=standby`, like the ATA and SAT types (FR-203, [ADR 0012](0012-read-only-and-coexistence-with-smartd.md), ADR 0004). A drive behind the controller can be a SATA or a SAS drive, and smartctl checks the power mode in both of its paths, so a drive in standby answers without data and is not woken. Such an answer is a standby answer: the probe reads on, because the device ID exists, and discovery keeps the previous state of the drive, so it produces neither a finding nor a `drive.missing`.
- **The configuration.** `[discovery] probe_cciss`, default `true`; it is the only key of the section that is not a list. `false` stops the probe, and the controllers are still named in `scan` and `doctor`. The drives that only the probe can find are then forgotten silently, without a `drive.missing` and without a recovery, like the drives of an exclude rule; when the probe is switched on again they are new records, and only a finding of their own is notified. A controller that the probe cannot reach (no SCSI generic node) is named by `doctor` as a warning; its drives are reported as missing after the runs of the policy, because the tool cannot tell which of them sat behind it. The probe is experimental in version 1 (ADR 0016).
- **The location and the field.** `pass_through_id` reads `N` from `cciss,N`, `sat+cciss,N` and `scsi+cciss,N`, and, for MegaRAID, from `megaraid,N`, `sat+megaraid,N` and `scsi+megaraid,N`; `scsi+` is the form the manual names for a cciss device whose implicit SAT is not wanted. So `scan` shows `Location: /dev/sg1 (hpsa), device 0` and a notification about one drive carries `device-id` = `N`, as [ADR 0029](0029-notification-field-device-id.md) says for every pass-through type.
- **The texts.** `scan` prints one `HPE Smart Array:` line per controller: the node and the IDs it read, or why it was not probed. `doctor` has the line `probe`: `ok` when there is no such controller, when the probe runs, or when it is switched off; `warn` when the probe should run and cannot (no SCSI generic node) or cannot be used (a `smartpqi` host), with the advice that names the way out; `skip` when sysfs cannot be read. The reason of the driver wins over the switch: a `smartpqi` host is a warning also with `probe_cciss = false`, because switching the probe on would not help it.
- **The evidence.** The source only, and synthetic fixtures: no output of an HPE host was ever recorded. The test frame derives the outputs of two drives from the recording of the maintainer's TrueNAS host and rewrites their device fields to the pass-through; an ID that the recording does not have is the empty bay, which the fake smartctl answers as smartctl does, with a failed open and exit status 2. The `--info` outputs of Starosdev/scrutiny stay evidence only ([Research 08](../research/08-public-recordings.md), [ADR 0026](0026-recordings-of-scsi-drives-and-of-other-projects.md)).

## Consequences

- A host with an `hpsa` controller in RAID mode monitors its physical drives without any configuration, and its notifications name the controller and the device ID, so a matcher can select one of them.
- A host with `smartpqi` is not monitored automatically. `scan` and `doctor` say so and name the manual entry; the tool claims nothing about whether the pass-through would work there (Q-R2).
- On such hosts the probe costs one smartctl call per drive and up to three failing calls in each run; a call that hangs costs its full timeout, so a wedged controller costs up to three timeouts per run. It is the only part of a run that reads a device the scan did not name, and a drive that the scan found as well is read twice in that run and kept once, through the scan.
- A drive in standby is not woken: every `cciss` form is read with `--nocheck=standby`, and the drive keeps its previous state for that run (FR-203, [ADR 0012](0012-read-only-and-coexistence-with-smartd.md)).
- Switching the probe off forgets the drives that only it can find, silently and without a recovery, so no false `drive.missing` is sent. Switched on again they are new records, and only a finding of their own is notified. A controller the probe cannot reach (no SCSI generic node) is a different case: the drives behind it are reported as missing after the runs of the policy, because the state does not say which drives sat behind which controller.
- A drive that is present but answers nothing is indistinguishable from an empty bay: it is not reported, and it costs one of the three failures. A controller with three such drives in a row is not probed further.
- How smartctl lists the logical volume of an HPE controller in the device scan is not recorded. The probe does not change that listing, the synthetic fixture lists nothing, and Q-R2 keeps the question.
- The probe is read-only like everything else: one call per device with the options of ADR 0004 and no option that changes a drive.

## Revisit when

- A source or a recording shows that `-d cciss,N` works with the driver `smartpqi`, or shows how an empty bay answers in the tool's own call and how the scan lists the logical volume; Q-R2 then closes.
- A recording of an HPE host exists: it becomes a fixture, and the synthetic one is replaced by it.
- A controller reports more than 127 devices, which smartctl itself does not accept.
