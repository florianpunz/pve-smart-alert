# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- `pve-smart-alert dump-fixture` replaces a device name that is not a node, such as a `/dev/disk/by-id/` link, a `/dev/mapper/` name (which can be a multipath WWID) or a `/dev/serial/by-id/` link, in the file name of its recording, in `recording.json` and in every text, and also the form in which udev writes spaces of a serial number as underscores (ADR 0039). A node such as `/dev/sda`, `/dev/nvme0n1` or `/dev/bus/6` stays, and a fixture keeps the file names its source gave it. The free text of `recording.json` is anonymized as well. The archive is readable by root only, and it replaces a symbolic link at its path instead of writing through it (NFR-14, [ADR 0023](docs/adr/0023-anonymization-of-recordings.md)).
- A reason that the notification system or the mail command gives for a failed delivery reaches the fallback mail cleaned and cut like a string of a drive: the answer of an external program could carry an escape sequence or a line of its own (ARCHITECTURE.md section 14).
- `check --dry-run`, `scan`, `status` and the progress line cut a device name, a smartctl type and the text of a finding to the length of a printed string. The text of `health.failed` carries the informational exception of a SCSI drive, which can be arbitrarily long.
- The template data of a notification carries the WWN of a drive cleaned like every other value.
- `config show` writes the value of a selector and a comment as a TOML string with its quotes and backslashes escaped, so that the line can be copied back into the configuration file.
- The failure reporter replaces control and format characters and the line and paragraph separators in the journal lines it mails, so that a traceback cannot put a terminal escape sequence or a forged line into the mail.
- The last good configuration, `last-good-config.json`, is written readable by root only, like the state file, and its directory is created with mode 0700 and corrected when an earlier build or a run by hand left it with the mode of the umask. It holds the selectors of the drives, with their serial numbers and WWNs, and the whole notification policy (ADR 0007, ADR 0011).
- `pve-smart-alert config show` names the last good configuration as the origin of the values it yields while the configuration file cannot be used, including the built-in defaults it fills in, and the header names its file, instead of crediting the values to the file that could not be used; without a last good configuration the built-in defaults apply (FR-406, FR-407).
- `pve-smart-alert check --dry-run` shows the findings of the correct drive when several drives are read through one controller and share a device name, such as two drives behind a MegaRAID controller; the notifications themselves already carried the right finding and device ID (FR-601).

## [0.5.0] - 2026-10-31

### Added

- [docs/hardware-support.md](docs/hardware-support.md) states for every controller family how its support was verified, with the evidence labels of ADR 0016, and how to record a host with `pve-smart-alert dump-fixture` and contribute the archive (NFR-16).
- `pve-smart-alert scan`, `pve-smart-alert doctor` and a notice `tool.unsupported_controller` name a controller whose drives smartctl cannot read, such as one with the driver `mpi3mr` (Broadcom MegaRAID 96xx, Dell PERC 12): its drives in RAID mode are not monitored, an upstream limitation of smartmontools (issue 313). The notice clears with a recovery when the controller is gone; a missing smartctl or an unreadable `/sys` does not clear it. HBAs such as `mpt2sas` and `mpt3sas`, `ahciem` and unknown drivers are not reported ([ADR 0030](docs/adr/0030-controllers-whose-drives-cannot-be-queried.md)). `doctor` reports this in a line `controllers` and no longer ends with a line `pending`. The notice also says how many drives the run monitors on the host, so that a host with nothing monitored next to the controller is told apart from a host whose remaining drives are fine, and it names the configuration key that switches it off for a controller in HBA mode, whose drives all appear in `scan` ([ADR 0031](docs/adr/0031-switching-tool-conditions-off.md)).
- The conditions of the tool itself, `tool.smartctl_missing`, `tool.smartctl_too_old`, `tool.scan_failed`, `tool.config_invalid`, `tool.state_reset`, `tool.transport_degraded` and `tool.unsupported_controller`, can be switched off with `enabled = false` under `[checks."<id>"]`, in the same table as the checks of a drive and with the same meaning; `pve-smart-alert config show` lists them with their state (FR-408, [ADR 0031](docs/adr/0031-switching-tool-conditions-off.md)).
- The drives behind an HPE Smart Array controller are found on hosts with the driver `hpsa` by probing `cciss,0` upwards on the SCSI generic node of the controller, experimental and on by default: `scan` names each controller with the drives it read or why it was not probed, `doctor` has a line `probe`, and a notification about such a drive names the controller and the device ID in `device-id` (FR-103, [ADR 0032](docs/adr/0032-hpe-smart-array-probe.md)). A controller with the driver `smartpqi` is named in `scan` and `doctor` and not probed; its drives can be added as `[[discovery.device]]`. `probe_cciss = false` in `[discovery]` switches the probe off, and the drives that only it can find are then forgotten silently instead of being reported as missing. A drive in standby behind the controller is not woken: every `cciss` form is read with `--nocheck=standby`, and a drive that answers so keeps its previous state (FR-203).
- A notification about one drive read as `megaraid,N`, `sat+megaraid,N` or `scsi+megaraid,N` behind a MegaRAID controller, or as `cciss,N`, `sat+cciss,N` or `scsi+cciss,N` behind an HPE Smart Array controller, carries the field `device-id` with the device ID `N`, so that a matcher can select one drive behind the controller ([ADR 0029](docs/adr/0029-notification-field-device-id.md), [ADR 0032](docs/adr/0032-hpe-smart-array-probe.md)). The field `device` stays the node of the controller. A drive behind another controller, such as 3ware, Areca, Adaptec, HighPoint or SSSRAID, has no such field, and neither has a notification that is not about one drive ([ADR 0034](docs/adr/0034-manual-entries-of-other-pass-through-types.md)).
- `pve-smart-alert --version` prints the version of the tool.
- `pve-smart-alert test-notification` sends one test notification with a selectable severity and reports what the notification system did with it (FR-520).
- Notifications reach the Proxmox VE notification system through a Perl bridge that calls `PVE::Notify`, with mail to root as the automatic fallback when that route fails ([ADR 0008](docs/adr/0008-notification-integration.md)).
- The two pass-through templates of the tool are installed into the template directory of the notification system.
- `pve-smart-alert doctor` reports the state of the configuration, the notify bridge, the notification templates and the mail command (FR-603).
- A Debian package with a launcher, the bridge, the templates and the configuration file; `make build` builds it together with the Python distribution ([ADR 0013](docs/adr/0013-packaging-and-installation.md)).
- `pve-smart-alert doctor` reports the routing of the notifications: it reads the matchers and targets through `pvesh` and warns when a severity of the tool reaches no target, because the notification system drops such a notification without an error ([ADR 0020](docs/adr/0020-routing-check.md)). With `transport = mail`, the line `routing` checks the route of mail to root, which every notification takes then.
- `pve-smart-alert test-notification` names the matchers that route the test notification, or says that none does; a test that went as mail is followed as the notification that mail to root becomes. When the notification system logged nothing, it points out that an empty log can mean that no matcher matched.
- The configuration accepts `[smartctl]` with `path`, `timeout` and `detail`, and manual devices in `[[discovery.device]]` (FR-104); the reference configuration documents them.
- `pve-smart-alert scan` shows every device found with its source and what became of it, and for each drive its model, serial number, class, what uses it, its wear value with the source and, where it differs, the value of the web interface (FR-108).
- `pve-smart-alert dump-fixture` records the device scan, lsblk and the output of smartctl for all or selected drives as one archive, with serial numbers, WWNs and UUIDs replaced by placeholders, and writes nothing when a real value would be left (FR-604, [ADR 0023](docs/adr/0023-anonymization-of-recordings.md)).
- `pve-smart-alert doctor` reports smartctl with its version and fails for a smartctl older than 7.0.
- Discovery finds the drives of a host from the device scan of smartctl, the probe for HPE Smart Array controllers and the manual devices and reads them in the order scan, probe, manual entries; a drive that two sources find is read twice and kept once. It adds transport, links and the volume group, pool or array from lsblk, skips remote devices, devices that are not disks, drives without SMART and drives an exclude rule selects, and keeps a drive reached through several paths once ([ADR 0005](docs/adr/0005-drive-discovery-and-identity.md)).
- The configuration accepts exclude rules in `[discovery]`, which select drives by model pattern, serial number or WWN ([ADR 0024](docs/adr/0024-drive-selectors.md)).
- The wear value of an SSD comes from `endurance_used`, the device statistics or the NVMe health log, and only then from a vendor attribute, with its source, and the value the web interface shows is kept next to it ([ADR 0021](docs/adr/0021-wear-value-source.md)). For ATA, the value of `endurance_used` counts as the vendor-neutral source only when the device statistics were read; a guess of smartmontools without them is named as the vendor attribute it is ([Research 03](docs/research/03-smart-indicators.md)).
- `pve-smart-alert doctor` reports the route of the fallback in a line `fallback`: whether a matcher routes mail to root, which arrives as `system-mail`, and whether `/root/.forward` hands it to the notification system ([ADR 0022](docs/adr/0022-fallback-routing-check.md)).
- When a matcher would route a notification but it or its targets are disabled, `pve-smart-alert doctor` and `pve-smart-alert test-notification` name it instead of advising a new matcher.
- `pve-smart-alert check --dry-run` evaluates every drive against the checks of the [check catalog](docs/check-catalog.md) and prints the findings with their check, severity, value and threshold, and the notifications a run would send now; it sends nothing and changes no state (FR-601).
- The evaluation: a catalog of independent checks with stable identifiers, the drive's own failure verdict always critical, raw defect counters with thresholds from published failure rates, wear capped at warning, and missing data never a finding ([ADR 0010](docs/adr/0010-health-evaluation-and-default-thresholds.md)). The command timeouts of attribute 188 are read decoded where the drive packs them (Q-T1).
- The configuration accepts the global overrides of `[checks."<check-id>"]`: `enabled` and the thresholds `notice`, `warning` and `critical`, one number or, for the temperature, a table of the drive classes (FR-402).
- The configuration accepts per-drive overrides in `[[drive]]`, selected by model pattern, serial number or WWN: `exclude` leaves the drive unmonitored, `detail` reads it with another smartctl detail level, and `checks` overrides any check for that drive (FR-403).
- `pve-smart-alert config check` validates the whole file and exits non-zero on errors, which name the key and the line (FR-405). `pve-smart-alert config show` prints every key with its effective value and its origin, the file or the built-in default, and `--defaults` prints the built-in ones (FR-407).
- An invalid configuration file never stops a run: the last configuration that passed validation, saved as `last-good-config.json` in the state directory, or the built-in defaults are used and the error is reported (FR-406). An override that repeats the built-in default changes nothing.
- `pve-smart-alert check` runs one check and sends the notifications that are due, following the policy of [ADR 0009](docs/adr/0009-notification-policy.md): a problem once, again when its severity rises, when its value worsens after a cool-down, and as a reminder per severity; a recovery when it has cleared; one message per drive and one summary above the grouping limit; one summary on the first run (FR-509 to FR-516). A notification that is not handed over is planned again on the next run (FR-517). Each run logs one summary line (FR-606), and a second run while one holds the lock exits with status 3 (FR-605).
- The state of the tool is kept in `/var/lib/pve-smart-alert/state.json`, replaced atomically; a corrupt file is set aside and the next notification is one summary ([ADR 0007](docs/adr/0007-state-storage.md), NFR-11, NFR-12).
- The event checks `ata.crc_errors`, `ata.error_log`, `nvme.thermal_excursion` and `nvme.error_log` report a rise of their counter above the baseline of the state; the value a drive has when it is first seen never alerts (FR-306).
- A drive that is absent for two runs is reported as missing, once, and one without usable data for two runs as unreadable (FR-309, FR-310). Both are checks of the catalog, `drive.missing` and `drive.unreadable`, and can be switched off.
- Problems of the tool itself are notified under the same policy: smartctl missing or too old, a failed device scan, an invalid configuration, a notify bridge that cannot be used, and a state file that was reset (FR-518).
- The configuration accepts the settings of the notification policy in `[notify]` and `[notify.reminder]`, and the confirmation count `confirm_runs` of a condition check (FR-404).
- `pve-smart-alert status` shows the last run and every drive with its active conditions from the state, and `--json` prints the state (FR-602).
- `pve-smart-alert doctor` reports the state file and the last run in a line `state`.
- The package installs a systemd timer that runs `pve-smart-alert check` 3 minutes after boot and every 30 minutes after that, and enables and starts it on installation ([ADR 0006](docs/adr/0006-scheduling.md)). A run skipped because another one holds the lock counts as a success.
- A failed run, including one that could not hand over a notification, is reported by a short mail to root that does not use the code of the tool, at most once a day and once more after a reboot ([ADR 0009](docs/adr/0009-notification-policy.md)).
- `pve-smart-alert doctor` reports the timer in a line `timer`: whether it is installed, active and enabled, its schedule with drop-ins, and the next run (FR-603).
- Purging the package also removes `/run/pve-smart-alert/`.
- The check service runs with the systemd sandboxing options of [ADR 0025](docs/adr/0025-sandboxing-of-the-check-service.md); the drives and the mail queue stay reachable.
- `pve-smart-alert doctor` also reports the version of Proxmox VE, and whether smartd is active and mails root, which reports some problems twice; the README says how to quiet smartd by hand (FR-603, [ADR 0012](docs/adr/0012-read-only-and-coexistence-with-smartd.md)).
- `install.sh` installs the newest release, or a pinned one, after verifying the checksum of the package ([ADR 0013](docs/adr/0013-packaging-and-installation.md)).
- SAS and parallel SCSI drives are monitored: their grown defect list, their uncorrected read, write and verify errors and, where the drive has the page, their pending defects are checked against the thresholds of the [check catalog](docs/check-catalog.md), together with the health verdict, the temperature, the self-test log and the endurance indicator of SAS SSDs. A SAS drive without a health verdict is not counted as failed, and a failed one names the exception the drive reports. A SAS drive whose informational exceptions are switched off gets the notice `smart.disabled`, which says so and names `smartctl -s on`. Until now such drives were unreadable; a run therefore clears their `drive.unreadable` condition once, with a recovery message.
- Drives behind a MegaRAID controller, read as `megaraid,N` (SAS) or `sat+megaraid,N` (SATA), are monitored, and `scan` and the notifications name the controller with its driver and the device ID, such as `/dev/bus/6 (megaraid_sas), device 14`. A changed device ID keeps the drive and its state. A drive in JBOD mode, reachable as a block device and through the controller, is kept once ([ADR 0028](docs/adr/0028-logical-volumes-and-enclosures.md)).
- Logical volumes of RAID controllers are skipped as `logical-volume`, recognized by their vendor and model in lsblk or in their drive output, or by the message of the scan, and devices read as SCSI that are no disk, such as enclosures, as `not-a-disk` ([ADR 0028](docs/adr/0028-logical-volumes-and-enclosures.md)).

### Changed

- `pve-smart-alert dump-fixture` also replaces the logical unit id and the SAS addresses of SCSI and SAS drives by placeholders, and writes nothing when one of them has a form it does not know ([ADR 0026](docs/adr/0026-recordings-of-scsi-drives-and-of-other-projects.md)).
- `pve-smart-alert check` shows which drive it reads only on a terminal; a run of the timer logs its summary line and no line per drive (FR-606).
- `pve-smart-alert doctor` reports a configuration file that does not validate as a warning that says which configuration a run continues with, instead of failing: monitoring does not stop (FR-406).

### Fixed

- A command interrupted with Ctrl+C says `pve-smart-alert: interrupted` on standard error and exits with status 130, instead of ending in a traceback; `doctor` ended so when it was interrupted inside `pvesh`.
- The one-command installation says what became of the package instead of always announcing an installation and a first check: the version is installed already, the package changed from one version to another, it was installed again, or apt did not finish, with the state dpkg reports. It also refuses to hand apt a package whose name is not `pve-smart-alert` or whose version is not the pinned one.
- `apt purge` also removes `/usr/share/pve-smart-alert`, so that a byte code cache written there by a Python run that bypassed the launcher no longer keeps the directory after the purge. Anything else that an administrator put below that directory goes with it ([ADR 0035](docs/adr/0035-purge-removes-the-package-directory.md)).
- The package installs the manual page as `/usr/share/man/man8/pve-smart-alert.8.gz`, the path that the documentation named and that no package carried until now.
- The package installs the reference configuration as `/usr/share/doc/pve-smart-alert/config.reference.toml`, the path that `doctor`, the shipped `config.toml` and the documentation name; it was installed compressed, as `config.reference.toml.gz`.
- `pve-smart-alert scan`, `status`, `check` and `check --dry-run` no longer print the control characters of a drive's model, serial number, firmware, of the label of a pool or of the inquiry data of a logical volume, such as an ANSI escape sequence or a newline, nor the format characters of Unicode that change the order or the width of text, and cut such a value at 200 characters as a message does; notifications and their fields drop these characters as well, among them the C1 controls, and a device of the scan whose name fails its check is shown cleaned, also in the data of the bridge. A lone surrogate in such a string no longer ends `scan`, `status`, `check` or the dry run with an encoding error. `test-notification` and the journal lines of a run clean what a transport answered. The state file writes the characters that the outputs remove as escapes, and a mail that cannot be built is reported as not delivered instead of ending the run.
- `pve-smart-alert config check` names the line of an unknown check identifier, as it does for every other configuration error (FR-405).
- The wear of an ATA drive read with `smartctl.detail = "basic"` no longer claims the vendor-neutral source: without the device statistics, smartmontools guesses `endurance_used` from a vendor attribute, and the guess is shown as the vendor attribute it is.
- A run with an invalid configuration and no last good configuration says that the built-in defaults are in use, instead of claiming a last good configuration (FR-406).
- A drive behind an Adaptec or HighPoint controller, or behind 3ware in its deprecated form, read through a manual entry on a block device such as `aacraid,0,0,2` on `/dev/sda`, no longer takes the location, the ZFS pool, the volume group or the inquiry data that lsblk shows for that node, which is the logical volume of the controller, and is no longer skipped as a logical volume because of them ([ADR 0034](docs/adr/0034-manual-entries-of-other-pass-through-types.md)).
- A drive behind 3ware, Areca, Adaptec, HighPoint or SSSRAID is read with `--nocheck=standby`, as a drive behind HPE Smart Array is, so that a drive in standby behind such a controller is not woken where the controller carries the power mode check (FR-203, ADR 0034).
- A SAS drive in standby that `--nocheck=standby` leaves alone, such as one behind HPE Smart Array, is in standby, not unreadable: smartctl names its power condition in words, such as `STANDBY BY TIMER`, which the tool did not recognize, so after two runs it reported the drive as unreadable.
- `pve-smart-alert dump-fixture` names in `recording.json` the device and type each drive was read with, not the type smartctl writes into its output, which differs for the drives behind HPE Smart Array, 3ware, Areca, HighPoint and, for a SATA drive, Adaptec and SSSRAID; a recording of such a host now replays.
- The finding `smart.disabled` of a drive behind a controller names the command with its type, such as `smartctl -s on -d aacraid,0,0,2 /dev/sdc`; without it the command addressed the logical volume or the controller.
- A JMicron RAID type, `jmb39x`, `jmb39x-q`, `jmb39x-q2` or `jms56x`, never reaches smartctl: a manual entry with it is refused as invalid configuration, and a last good configuration drops it. smartctl reads such a drive by writing to a sector of the RAID volume, and the tool only reads drives ([ADR 0012](docs/adr/0012-read-only-and-coexistence-with-smartd.md)).
